# Bezvody — карта проекта и правила репозитория

Карта записана 30.08 по заданию владельца. Ниже неё — действующие правила
безопасности и работы (они старше карты и при расхождении главнее).

## Что это за проект

**«Без воды»** — приложение о питании, тренировках и здоровье для
русскоязычного пользователя: дневник еды с общим каталогом продуктов,
генератор силовых программ с подсказкой веса и прогрессией, вес/замеры/шаги,
напоминания, ИИ-помощь (разбор еды по фото/голосу, подбор веса). Делает один
владелец без команды, 2–5 часов в неделю; живых пользователей двое — он и его
жена (закрытая бета). Продукт продаёт приватность: данные о здоровье не
уходят третьим лицам, чувствительные заметки шифруются на клиенте (E2EE-vault).

Стек намеренно минимальный: **весь клиент — один файл `index.html`
(~2.2 МБ: разметка, стили и ванильный JS), рантайм-зависимостей ноль.**
PWA (service worker, офлайн, установка на домашний экран). Бэкенд —
Supabase (Postgres + Auth, всё под RLS) и четыре serverless-функции Vercel.
Медиа — Cloudflare R2 через прокси `/media`. Деплой — Vercel автоматически
из `main`; buildCommand — это тест-гейт, красный гейт = нет деплоя.

Версия приложения (сейчас v679) прошита в `index.html` и `sw.js` и
поднимается в обоих одновременно — иначе PWA-кэш отдаст людям старьё.

## Карта кода

| Путь | За что отвечает |
|---|---|
| `index.html` | Всё приложение: экраны (Еда, Зал, Тело, Здоровье, Коуч), стили, логика, база упражнений. Единственный большой исходник |
| `sw.js` | Service worker: офлайн-кэш; имя кэша содержит версию |
| `manifest.json`, `icon.svg`, `icons/`, `fonts/` | PWA-манифест, иконки (PNG для iOS), шрифты woff2 |
| `api/ai.js` | Прокси к Anthropic для пользователей без своего ключа: вход по Supabase-токену, дневные/месячные лимиты, модель зажата сервером |
| `api/steps.js` | Приёмник шагов из iOS-команды (личный код + число, без аккаунтов) |
| `api/push-key.js`, `api/push-send.js` | Веб-пуши: публичный VAPID-ключ и рассылка по крону (RFC 8291/8292 на голом node:crypto, без пакетов) |
| `tests/` | Гейт качества, подробнее в «Командах» |
| `scripts/ship.js`, `scripts/sync.js` | Отправка одной командой (гейт→коммит→пуш) и утреннее «подтяни и напомни» |
| `supabase/` | Применённые миграции, `schema_reference.sql` — слепок схемы, `metrics.sql` — витрина цифр для ворот (`select * from metrics.pulse`); сама база одна, облачная |
| `promo/` | Промо-страницы: `/about`, `/studio`, `/reel`, `/privacy`, `/terms` (rewrites в vercel.json) |
| `capacitor.config.json` | Манифест будущей нативной сборки (v622): appId, цвета подложки, клавиатура поверх интерфейса. В веб НЕ публикуется; нативного проекта пока нет |
| `vercel.json` | Деплой: buildCommand=гейт, outputDirectory=`dist`, прокси `/sb`→Supabase и `/media`→R2, лимиты функций, заголовки |
| `server/` | VPN-скрипты владельца для его сервера — к приложению не относятся |
| `frontend-kit/`, `full-library-metadata/` | Заготовки клиентского кода и метаданные библиотеки упражнений |
| `.github/workflows/security.yml`, `skills.yml` | CI: gitleaks по всей истории, гейт и настоящий Chromium (Node 22) на каждый пуш; сканер скиллов — отдельным workflow только при изменении `.claude/skills` (минуты Actions, 23.09) |
| `.claude/skills/` | Скиллы агента (см. раздел «Скиллы проекта» ниже) |

Точки входа: пользователь — `index.html`; сервер — четыре файла в `api/`;
сборка — `tests/build.js` (копирует публичные файлы в `dist/`).

## Команды

```bash
node scripts/sync.js        # начало работы на машине владельца: pull + напоминалки
# Тест-гейт — тот же, что buildCommand на Vercel. Зелёный — обязателен перед пушем:
node tests/smoke.js && node tests/field.js && node tests/kitchen.js && node tests/matrix.js && node tests/build.js
node tests/matrix.js --baseline  # ТОЛЬКО когда выход генератора стал лучше, в том же коммите
node tests/dirty.js         # ДОПОЛНИТЕЛЬНО при правке расчётов (нужен Chromium)
node tests/browser.js       # ДОПОЛНИТЕЛЬНО при заметной правке интерфейса (нужен Chromium и Node 22+)
node tests/live.js --selftest  # проверить замок живого прогона (доступы НЕ нужны)
node tests/live.js             # ПРОГОН ПО ЖИВОМУ АККАУНТУ: вход, расшифровка, реальные дни.
                               # Доступы — только из BV_LIVE_EMAIL/BV_LIVE_PASS (.env.local или
                               # переменные среды). Пароль агенту НЕ говорится: из него выводится
                               # ключ шифрования хранилища. По умолчанию ТОЛЬКО ЧТЕНИЕ — запрет
                               # стоит в прокси, а не в коде страницы. Подробности — SETUP.md §7.
node tests/live.js --cost      # цена «перечитать всё» и полной отрисовки на ЖИВЫХ объёмах, мс
node tests/audit.js         # ОБХОД БЕЗ ПОВОДА: мёртвые и немые кнопки, функции без строки в SPEC.md
node tests/audit.js --list  # опись листов — из неё пишется SPEC.md
npm run ship -- "сообщение" # гейт → commit (pre-commit: detect-secrets+gitleaks+smoke) → push
```

Что проверяет гейт: `smoke` — рендер в фейковом DOM и накопленные инварианты;
`field` — полевые сценарии; `kitchen` — кухня; `matrix` — 180 сборок программ
против храповика `tests/matrix.baseline.json` (хуже — красный); `build` — сборка `dist/`;
`browser`/`dirty` — настоящий Chromium (второй — на заведомо битой базе),
в деплой-гейт не входят, без Chromium честно говорят «пропущен».
`audit` — обход БЕЗ повода: гейт помнит прошлые поломки, обход ищет новые
(мёртвая кнопка, немая кнопка, функция без строки в `SPEC.md`). Это отчёт,
а не ворота: он ничего не запрещает и в деплой-гейт тоже не входит.
**Линтера нет сознательно:** исходник один и это HTML со встроенным JS,
синтаксис и рендер ловит смоук. Деплой руками не делается никогда —
только автодеплой Vercel из `main`.

## Рабочий цикл с владельцем (принят 30.08)

Владелец формулирует хотелку коротко, без ТЗ; всё остальное — работа агента.

1. Агент делает всё в отдельной ветке: роли → логика до кода → код →
   гейт → ревью диффа → пуш.
2. Vercel сам собирает **preview** на каждый пуш ветки — стабильный адрес
   вида `bezvody-git-<ветка>-harddurants-projects.vercel.app` (точную ссылку
   агент называет в отчёте). Превью закрыты Vercel-логином владельца —
   это осознанно, не отключать.
3. Владелец смотрит готовый продукт по preview-ссылке с телефона.
4. **Его «ок» по preview = разрешение смержить ветку в `main`** (автодеплой
   в прод). Без «ок» в `main` не едет ничего — это то же правило
   «в main без явного слова владельца», склеенное с оценкой продукта
   в одно действие.
5. Каждое замечание владельца рождает починку класса плюс правило в гейте.

### Модель под задачу — называется до начала (решение владельца 27.09)

Агент сам модель не переключает, переключает владелец (`/model`). Поэтому
**первая строка ответа на новую задачу — рекомендация:** «Модель: …,
усилие: …, почему», и только после «начинай» — работа. Карта:

- Код (`index.html`, `sw.js`, `api/`, `tests/`): версия, починка по
  полевому отчёту, правило в гейте с мутациями, разбор по живым данным —
  **Fable 5.1** (или Opus 5.5, если Fable недоступна), усилие max.
- Аудит без правок кода (обход, замеры, ревью диффа и безопасности) —
  Fable 5.1 / Opus 5.5, усилие high.
- Только документы (`NEXT.md`, `SPEC.md`, `STRATEGY.md`, `BUSINESS_PLAN.md`,
  промо, конкуренты, ответ по коду без правки) — **Sonnet 5**, усилие high.
- Мелочь без риска (опечатка в тексте, строка в `NEXT.md`, номер версии) —
  Sonnet 5, усилие medium.
- Haiku здесь не применяется: исходник на 2,3 МБ со стендами, экономия на
  модели съедается починкой.

Экономия токенов идёт не от модели, а от объёма: чтение исходника, живые
прогоны, Chromium, мутации. Дешёвый формат задачи — одна фраза про одну
проблему, без «посмотри всё». Если задача сменила класс посреди работы
(документ вырос в правку кода) — агент останавливается и называет модель
заново.

### Три потока работы (решение владельца 23.09)

Вопрос владельца был «чат на каждую вкладку». Ответ — три потока по ТИПУ
работы, а не по экрану: один исходник на 2,3 МБ, общий гейт и один номер
версии не переживут пять параллельных правок, а половина задач сшивает
вкладки (шаги, расход, коуч).

1. **Продукт** — один рабочий поток, версии идут последовательно. Граница
   «внутри своего экрана» держится ролью-скиллом, а не чатом: `gym-coach`
   («Зал»), `kitchen-nutritionist` («Еда»), `body-doctor` («Тело» и
   «Здоровье»), `coach-desk` («Коуч»). Сессия, начатая с «работаем над
   Едой», грузит скилл и получает свою очередь из `NEXT.md` («до уровня
   Nike/Hevy», подраздел вкладки), свои строки `SPEC.md` и свои стенды.
   Общий код правится только когда иначе нельзя и называется в отчёте.
2. **Аудит** — без чата, по расписанию (Routine среды Claude Code,
   понедельник 06:00 МСК): свежая сессия гоняет весь гейт, `audit.js`,
   Chromium, `live.js --cost`, ревью безопасности по диффу недели, кода
   не правит и пишет раздел «Аудит недели» в `NEXT.md` (коммит только
   документа). Владелец читает три строки в понедельник. Расписание
   заведено 23.09: `trig_01VBPoVxR5D5dHwqiDe8FDdM`, cron `0 3 * * 1` (UTC),
   первый запуск 28.09; пуш на телефон по итогу. Выключить или поправить —
   в claude.ai → Routines, либо из сессии командой обновления расписания.
3. **Стратегия и запуск** — отдельный чат, может идти параллельно с
   продуктовым. Правило разделения: этот поток правит только `STRATEGY.md`,
   `BUSINESS_PLAN.md`, `SBER_APPLY.md`, `APPS.md`, `promo/` и рынок;
   в `index.html`, `sw.js`, `tests/`, `api/` не заходит никогда.
   Продуктовая находка из этого чата — строкой в очередь `NEXT.md`.

Чаты по вкладкам, если владелец всё же захочет, — только ветки
`tab/<экран>` с мержем строго по одной и номером версии при мерже.

## Источники истины

Прежде чем спрашивать владельца — смотри сюда, в этом порядке:

1. `NEXT.md` — рабочая доска: что висит на владельце, очередь работ,
   журнал версий. Читается первой в каждой сессии.
2. `SPEC.md` — реестр обещаний: что каждая функция ОБЯЗАНА делать, одной
   строкой. Заведён 02.09. Читается перед тем, как чинить или менять функцию:
   расхождение кода с обещанием — это баг; расхождение обещания с замыслом —
   решение владельца. Новая функция без строки здесь — находка обхода.
3. `COUNCIL.md` — кто решает (роли, вето, порядок голосов).
4. `CRAFT.md` — как делаем (код, проверки, дизайн, функции).
5. По задаче: `GYM.md` (факты о зале владельца — рядом со скиллом gym-coach) ·
   `ARCHITECTURE.md` + `supabase/schema_reference.sql` (схема БД) ·
   `SCENARIOS.md` (десять сценариев дня на «Еде»: что видит, где спотыкается, что сделано; заведён 26.09) ·
   `PROGRAM_AUDIT.md` (аудит подбора программ: замер по 180 сборкам, восемь недель владельца по 1ПМ и объёму, разрыв с персональным тренером и план из шести шагов; заведён 26.09) ·
   `NAVIGATION.md` (матрица состояний навигации PWA против HIG, аудит 14.09) ·
   `AUDIT_POINT_A.md` (сквозной аудит «Точка А» v601: реестр 34 листов и оверлеев,
   графы путей, 37 нативных диалогов — все сняты в v602–v603, производительность, дорожная карта) ·
   `STRATEGY.md` (рынок и позиционирование) · `SECURITY.md` (если утёк
   секрет) · `SETUP.md` (новая машина) · `HANDOFF.md` (напоминалки) ·
   `BUSINESS_PLAN.md` (куда идём и на какие деньги).

## Ограничения — где ошибка дорого стоит

Минимум; подробности — в разделах ниже, они главнее краткой выжимки.

- **В `main` не коммитить без явного слова владельца** (правило владельца,
  30.08). Работа — в отдельной ветке; «ок» владельца по preview-ссылке =
  разрешение на мерж (см. «Рабочий цикл»).
- **Секреты:** `.env*`, ключи, credentials — не читать, не печатать.
  `service_role` — никогда в клиент и никогда в git.
- **База:** каждая пользовательская таблица — под RLS с проверкой владельца.
  Ошибка здесь = чужие данные о здоровье наружу, это конец продукта.
- **Зависимости:** рантайм-зависимостей ноль, и это решение, а не случайность.
  Не `curl | bash`, не случайные `npx -y`.
- **Новая функция или параметр — по чек-листу CRAFT §1 «Первая постройка
  чистой»** (решение владельца 27.09): контракт в `SPEC.md` до кода, пять
  строк от роли-практика, пространство входов и матрица-стенд до кода,
  замер выхода числом и воротами (`tests/matrix.js`); правка, требующая
  защиты в трёх местах, — стоп и перестройка, а не заплата. Следующий шаг
  предлагается только под полевой отчёт или измеренную проблему.
- **Перед пушем:** гейт зелёный, секрет-скан пройден, версии в `index.html`
  и `sw.js` подняты вместе.
- **Ничего не публиковать и не деплоить руками** — деплой только автодеплоем
  из `main`, публикации наружу только по решению владельца.

# Правила безопасности репозитория Bezvody

Контекст: одностраничное PWA (index.html) + Supabase (Postgres/Auth) + Vercel.
На клиенте — только публичные ключи. Данные о здоровье шифруются на клиенте (E2EE-vault).

## Секреты
- НИКОГДА не клади реальные доступы в отслеживаемые git-файлы.
- В клиент попадает ТОЛЬКО `publishable`/`anon` ключ Supabase — он публичный by design и защищён RLS.
- `service_role` — никогда в клиент, никогда в git. Только панель Supabase / Edge Functions.
- AI-ключ Anthropic — вводит пользователь, хранится на его устройстве. Не хардкодить.
- Не читай, не печатай, не пересказывай значения из `.env*`, `*.pem`, `*.key`, `credentials*.json`,
  `token.json`, `secrets*.json`, `.mcp.json` без явного узкого разрешения пользователя.
- Считай `.gitignore` правилом для Git, а не границей конфиденциальности.

## База данных (главный риск — broken access control)
- Каждая таблица с пользовательскими данными обязана иметь RLS с проверкой владельца
  (`user_id = auth.uid()` или membership), НЕ `using(true)`.
- `using(true)` допустим только для чтения общих справочников (products/recipes/packages).
- Пользователь не может сам выставить `verified`/`official` — только привилегированным путём.
- После любой миграции проверяй политики: `select * from pg_policies where schemaname='public'`.

## Перед пушем/публикацией
- Прогоняй секрет-скан (detect-secrets / gitleaks) перед коммитом и пушем.
- Тест-гейт (`node tests/smoke.js && node tests/field.js && node tests/kitchen.js`) обязан быть
  зелёным — он же buildCommand на Vercel.
- **Заметная правка интерфейса — прогон `node tests/browser.js`** (правило выведено 18.08):
  настоящий Chromium через CDP, без npm-зависимостей. Фейковый DOM ловит краши и расчёты,
  но не знает, ЧТО человек видит: простой режим v265 по разметке выглядел урезанным, а в
  браузере первые экраны новичка оказались почти как в полном. В деплой-гейт не входит —
  на Vercel браузера нет; нет Chromium локально — тест честно говорит «пропущен».
- **Правка расчётов — прогон `node tests/dirty.js`** (правило выведено 19.08):
  настоящий браузер с заведомо битой базой — строки вместо чисел, NaN, null,
  кривые и будущие даты. Краш на одной такой записи отрезает человека от всей
  истории. Ловит только НЕОБРАБОТАННЫЕ исключения: то, что приложение глотает
  в try/catch, он не увидит — поэтому найденные им инварианты переезжают в
  `tests/smoke.js`. В деплой-гейт не входит (на Vercel браузера нет).
- **Самопроверка диффа перед пушем** (правило владельца, 28.07): для содержательной
  правки — прогон ревью (/review) по диффу до пуша: логика, крайние случаи,
  «а как это выглядит для человека». Раз в неделю — /security-review по
  накопленным изменениям. Полевую обкатку это дополняет, не заменяет.
- **Правка класса, а не места** (правило владельца, 03.08): полевой отчёт о
  неудобстве — повод закрыть весь класс проблемы одним решением (глобальный
  фикс + правило в тест-гейте), а не подкрутить место, куда ткнул владелец.
  Примеры: «0 не убирается» → select-on-focus для всех числовых полей;
  «стена чипов» → анти-бардак-скан в смоуке. Владелец не обязан подсвечивать
  каждый экземпляр.
- **Логика — до сборки** (правило владельца, 28.07): перед новой фичей —
  письменный прогон полевого сценария глазами пользователя («что он увидит,
  что нажмёт, где споткнётся»), и только потом код. Особенно для всего, что
  показывает еду, веса и деньги: цифра без здравого смысла хуже её отсутствия.
- Если секрет утёк в чат/лог/историю: сначала ротация ключа, потом чистка. См. SECURITY.md.

## Два правила фундамента

Этот файл — рабочие правила репозитория. Над ним стоят два документа,
и при расхождении главные они:

- **`COUNCIL.md`** — кто решает. Роли двух разрядов: шесть **решающих**
  (тренер, нутрициолог, врач, удержание, редактор экрана, скептик, продукт)
  с юрисдикцией и вето и двое **стерегущих** (инженер — данные человека и живучесть;
  хранитель справочников — качество базы движений и продуктов), которые не
  решают, но останавливают выпуск. Карта ответственности покрывает три
  фронта плюс два: физическое, техническое, данные, как человек это читает,
  продукт и деньги — у каждого один хозяин. Роль заводится тогда и только
  тогда, когда у неё есть свой предмет спора: дизайнер отдельно не заведён
  (тон и композиция не спорят — это редактор экрана), продукт заведён
  (с удержанием расходится регулярно).
  Порядок голосов: **роли приносят отчёт → руководитель опергруппы решает
  → владелец закрывает**. **Задача владельца — вход, а не приказ на
  исполнение:** прогон через роли обязателен для всего, что меняет видимое
  или делаемое человеком, для новых правил и для здоровья; опечатки,
  рефакторинг и внутреннее идут мимо. Владельцу идёт решение, цена и чьё
  возражение отклонено, а не протокол. Руководитель обязан назвать решение вслух и
  письменно назвать отклонённое возражение с причиной; выше него только
  вето врача по здоровью и вето владельца без обоснования.
  Ключевое: противоречие между ролями — это баг, а не разница мнений;
  **слово владельца последнее**, и он не должен находить поломки первым —
  каждый его отчёт даёт не только починку, но и правило. У ИИ своего мнения
  нет: он говорит от роли и не может опрокинуть её расчёт.
- **`CRAFT.md`** — как делаем. Код, проверки, дизайн, функции. **С 21.09 открывается
  «Кодексом 12 правил Premium UI» — законом автора**, которому подчиняется любая
  правка в `index.html`, `sw.js` и `tests/smoke.js`: выжигание текстового шума
  (заблокированное читается opacity .72, а не подписью) · одно число на экране
  ровно один раз и разделение контекстов вкладок · цель нажатия 44 минимум,
  52–54 идеально, под большой палец одной руки · ленивый рендер, без layout
  thrashing и перерисовок списков целиком, отклик на ввод ≤ 15 мс. Там же —
  карта того, что из этого уже держит гейт, а что пока нет, и список побед
  с настоящими именами в коде. Ключевое:
  правило проверяет ВЫХОД, а не вход; правило, не поймавшее свою мутацию, —
  не правило; цифра без здравого смысла хуже её отсутствия.

Оба читаются в начале сессии вместе с `NEXT.md`.

    следом идёт второй запрос `/api/context/semantic` с промтом в виде поиска.

## Продуктовая работа (не только код)

Владелец делает продукт один, без команды и аналитиков. Значит анализ рынка —
часть нашей работы, а не факультатив.

### Рабочая доска — `NEXT.md`

`NEXT.md` — главный файл для владельца. Он заходит часто, но короткими
подходами, и держать всё в голове между сессиями не может. Помнить должен файл,
а не человек.

- **В начале каждой сессии:** прочитай `NEXT.md` и первым делом назови,
  что висит на владельце (красный список). Коротко, без пересказа всего файла.
- **В конце каждой сессии:** обнови его — журнал версий, галочки в плане
  месяца, очередь работ, дату и версию в шапке. Это не факультатив.
- Каждый пункт «на тебе» пиши с **честной оценкой времени**. «20 минут» и
  «два часа» — разные решения для человека с основной работой.
- Не раздувай: устаревший пункт переписывай, а не дописывай рядом.
- План рассчитан на **2–5 часов владельца в неделю**. Не предлагай темпа,
  которого он не выдержит — пропущенная неделя не должна ломать план.
- **Полевые проверки — не больше трёх** (правило владельца, 02.08): в конце
  сессии выдавай максимум 3 конкретные команды на завтра («открой X, нажми Y,
  должно случиться Z», с оценкой минут). Больше — только если владелец сам
  попросит. Очередь непроверенного живёт в NEXT.md, раздел «Проверить в поле»,
  и не теряется. Пятнадцать пунктов за раз — это не контроль качества,
  а перекладывание работы на владельца.

### В начале рабочей сессии
- Если сессия начинается с содержательной задачи (не мелкая правка) — коротко
  проверь, не появилось ли значимого на рынке: новые функции у конкурентов
  (MacroFactor, Cronometer, Hevy, Fitbod, MyFitnessPal, Яндекс/VK-фитнес),
  изменения правил RuStore/App Store, свежие данные по удержанию и ценам.
- Докладывай **только то, что меняет наши решения**. Без новостной ленты ради
  ленты: два-три пункта максимум, каждый — с выводом «что нам с этого».
- Если ничего значимого нет — так и скажи одной строкой и иди к задаче.

### Стратегия
- `STRATEGY.md` — живой документ: позиционирование, этапы, модель заработка,
  риски, ближайшие шаги. Обновляй его, когда:
  выяснилось что-то важное о рынке · пройден этап · изменилась гипотеза ·
  появились реальные цифры удержания.
- Не раздувай: если пункт устарел — переписывай, а не дописывай рядом.

### Как предлагать улучшения
- Сначала спроси себя: это бьёт в удержание первых 14 дней? Если да —
  приоритет высокий (пользователи с <3 тренировками за 14 дней уходят в 3-4 раза чаще).
- Всегда называй цену решения: время, деньги, риск. «Бесплатно» — тоже ответ.
- Честно говори, когда фича не нужна или преждевременна. Владелец ценит
  отказ с аргументом выше, чем услужливое «сделаю».

### Принцип контекста: человек в зале не выходит из тренировки

Человек с гантелей в руке не может листать вкладки, гуглить и вспоминать.

- **Всё, что нужно во время подхода, живёт внутри карточки упражнения**:
  суть (зачем, схема, задача дня), техника, подводящие, подсказка веса.
  Раскрывашка на месте, а не переход в другой раздел.
  **И обратная половина, добавлена 01.09 после замера:** только это и живёт.
  Правило читалось как «клади в карточку всё», и за месяц путь до первой
  строки подхода вырос до 443 px при экране в 700 — две трети до дела.
  История, разбор веса и всё, что открывают редко, живут в ЛИСТЕ упражнения
  (тап по названию). Предел пути стережёт `tests/browser.js`: не больше
  210 px до подхода и не больше одной раскрывашки перед таблицей.
- То же для разминки: у каждого движения инструкция по тапу. Движение без
  инструкции пропустят — значит, его как бы нет (тест это enforce'ит).
- Переход в другую вкладку допустим только для того, что во время подхода
  не нужно: видео (тап по названию), аналитика, настройки.
- Раскрытое состояние обязано переживать перерисовку экрана: записал
  подход — блок не схлопнулся.
- Тот же принцип на кухне: рецепт, граммовки и замены — внутри карточки
  блюда, а не «посмотри в другом месте».
