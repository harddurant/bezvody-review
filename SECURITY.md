# Безопасность Bezvody

## Модель
- Данные о здоровье шифруются на клиенте (AES-256-GCM, PBKDF2 310k). Сервер видит только шифроблоб.
- На клиенте — только публичный (anon/publishable) ключ Supabase. Доступ ограничен RLS на каждой таблице.
- `service_role` в клиент/репозиторий не попадает.
- AI-ключ Anthropic — пользовательский, хранится на устройстве, уходит напрямую в API Anthropic.

## Если секрет утёк (порядок действий)
1. Остановиться. Не копировать секрет повторно в чат/лог/задачу.
2. Определить тип: publishable/anon (публичный — ротация по желанию) vs. service_role/JWT-секрет/пароль (критично).
3. Немедленно ротировать критичный ключ в панели Supabase (Settings → API → Roll key). Сначала ротация, потом косметика.
4. Проверить зону поражения: что ключ мог читать/писать/удалять; посмотреть логи Supabase.
5. Просканировать текущие файлы и историю git (detect-secrets, gitleaks, trufflehog).
6. Если секрет в истории — переписать через git-filter-repo/BFG только после координации; force-push осознанно.
7. Включить GitHub secret scanning + push protection.
8. Зафиксировать инцидент: дата, источник, срок экспозиции, доступные данные, принятые меры.

## Сообщить об уязвимости
Приватно владельцу репозитория. Не открывать публичный issue с деталями.

## Известные остаточные риски
- `client_errors` принимает анонимные INSERT (телеметрия крашей) — теоретически можно засорить; влияние низкое,
  чтения через API нет. При проблемах — добавить rate-limit/ограничение размера или отключить anon-insert.
