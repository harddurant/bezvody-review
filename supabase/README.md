# Схема БД как код + безопасный деплой

## Файлы

- `schema_reference.sql` — человекочитаемый снимок всей схемы (таблицы, RLS, вью, функции). Для ревью в git. **Не источник правды** — им является история миграций в Supabase.

## Как получить канонические миграции в репозиторий (делается один раз)

Источник правды — история миграций в Supabase. Чтобы выгрузить её в `supabase/migrations/` без расхождений, нужен Supabase CLI (у тебя, требует пароль БД — у меня доступа к нему нет):

```bash
npm i -g supabase
supabase login
supabase link --project-ref SUPABASE_PROJECT_REF
supabase db pull          # выкачает всю схему в supabase/migrations/
git add supabase && git commit -m "schema as code" && git push
```

После этого любое изменение схемы делается как новая миграция и проходит через git — база перестаёт «меняться вслепую».

## Безопасный деплой (цель Фазы B)

- **Стейджинг перед продом.** Прежде чем катить миграцию в прод, проверяй на ветке БД:
  ```bash
  supabase db push --dry-run     # показать, что применится
  ```
  Либо заведи Supabase-ветку (branching) / отдельный стейдж-проект и проверяй там.
- **Vercel preview.** Каждая git-ветка → свой preview-URL для проверки; `main` → прод.
- **Бэкапы.** Проверь, что включены автоматические бэкапы БД (план Supabase).

### Открытый архитектурный вопрос (E2EE) — требует решения владельца
Ключ шифрования хранилища выводится из **пароля аккаунта**, а пароль уходит на Supabase Auth
при каждом логине. Значит теоретически тот, кто видит auth-эндпоинт (скомпрометированный
проект Supabase, логирующий прокси), может вывести ключ и расшифровать блоб — это слабее, чем
обещание «сервер не видит твои данные». Настоящий zero-knowledge требует **отдельной парольной
фразы хранилища**, независимой от пароля входа. Это несовместимо со старыми хранилищами
(нужна ре-шифровка) — поэтому не делается «по-тихому», выносится на решение.

Полная целевая архитектура и фазы — в `../TARGET_ARCHITECTURE.md`.
