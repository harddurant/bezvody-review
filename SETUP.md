# Bezvody — работа с проекта на нескольких устройствах

Проект живёт в облаке: код — GitHub (`harddurant/bezvody`, приватный), деплой — Vercel (авто из `main`),
база и авторизация — Supabase (`bezvody`, регион eu-central-1).

**Главное про базу:** она одна, облачная. Её НЕ нужно копировать на каждый компьютер.
Оба устройства подключаются к одному и тому же Supabase и видят одни и те же данные в реальном времени.
«Иметь базу на этом ПК» = просто запустить код, у которого прописаны URL и ключ Supabase (см. раздел 3).

---

## 1. Первый запуск на новом компьютере

Делается один раз на каждом устройстве, в твоём терминале (git авторизован под твоим GitHub).

```bash
# 1. Забрать код
git clone https://github.com/harddurant/bezvody.git
cd bezvody

# 2. Поставить зависимости (node_modules через git НЕ переносится)
npm install

# 3. Настроить подключение к Supabase — см. раздел 3
#    (либо .env, либо значения уже зашиты в коде — проверь, как в репозитории)

# 4. Запустить локально
npm run dev        # команда зависит от проекта — смотри "scripts" в package.json
```

Node на Vercel зафиксирован как 24.x — держи локально ту же мажорную версию.

---

## 2. Ежедневный ритм на двух устройствах

Единственное правило, от которого зависит «без проблем»:
**не отходи от компьютера с незапушенными изменениями.**

```bash
# Сел за работу:
git pull

# ...работаешь...

# Перед тем как встать:
git add -A
git commit -m "что сделал"
git push
```

После `push` Vercel сам пересоберёт и задеплоит. Supabase общий — ничего дополнительно синхронизировать не надо.

Если забыл запушить и на втором устройстве начал новые коммиты — история разойдётся,
при `push` будет конфликт. Лечится `git pull --rebase`, но проще не допускать: одно устройство = одна отправленная точка.

## 3. Подключение к Supabase (реальные значения проекта bezvody)

```
SUPABASE URL:            https://SUPABASE_PROJECT_REF.supabase.co
Publishable key:         sb_publishable_REDACTED
Legacy anon key (JWT):   <anon-key: публичный, берётся из панели Supabase → Settings → API>
```

Эти ключи публичные (клиентские) — их не страшно иметь на любом устройстве.
Реально секретный ключ — `service_role` — в код и в git попадать НЕ должен; он только в панели Supabase.

Как именно код читает эти значения — зависит от проекта. Найди в репозитории строку `createClient(`:
- если рядом `import.meta.env.VITE_...` → создай `.env` (см. `.env.example`), префикс `VITE_`;
- если `process.env.NEXT_PUBLIC_...` → префикс `NEXT_PUBLIC_`, файл `.env.local`;
- если URL и ключ вписаны прямо в JS → никакого `.env` не нужно, значения едут вместе с кодом,
  и раздел с env можно игнорировать (тогда настройка на новом устройстве = clone + install + запуск).

## 4. Изменения схемы Supabase

Если меняешь структуру БД (таблицы, RLS, политики) через панель Supabase или напрямую —
сохраняй каждое изменение как migration-файл и коммить в репозиторий. Иначе облако и код разойдутся,
и на втором устройстве ты не воспроизведёшь базу.
Если локальная БД тебе не нужна и всегда работаешь с облачной — этот пункт можно не соблюдать.

Уже применённые миграции (на 14.07.2026): `encrypted_vault_with_optimistic_locking`, `auto_confirm_emails_public`.

---

## 5. Нужен ли локальный Supabase?

Обычно нет. Для соло-проекта проще, когда оба устройства и прод смотрят в одну облачную базу.
Локальный стек (`supabase start`, Docker) нужен, только если хочешь ломать схему офлайн, не задевая прод —
но это добавляет обязанность строго вести миграции (раздел 4).

## 6. Серверные функции: ИИ-прокси и напоминания

Обе живут в `api/` и деплоятся Vercel'ом автоматически. Секреты задаются
**только** в Vercel → Project → Settings → Environment Variables и никогда
не попадают в git.

### 6.1. ИИ на нашем ключе (`api/ai.js`) — уже написано

| Переменная | Что это |
|---|---|
| `ANTHROPIC_API_KEY` | Ключ Anthropic владельца приложения. **Секрет.** |

После добавления ИИ работает для всех, кто вошёл в синхронизацию и добавлен
в таблицу `ai_allow` (закрытая бета). Свой ключ пользователя, если он его
ввёл, всегда имеет приоритет и идёт напрямую в Anthropic мимо нас.

Лимиты зашиты в код: 60 запросов на человека в день, 200 на всех.
Проверка доступа fail-closed — недоступна база, значит доступа нет.

### 6.2. Напоминания (`api/push-key.js`, `api/push-send.js`)

**Шаг 1. Сгенерировать пару ключей VAPID.** Локально, ничего не устанавливая:

```
node -e "const c=require('crypto');const{publicKey,privateKey}=c.generateKeyPairSync('ec',{namedCurve:'prime256v1'});console.log('VAPID_PUBLIC =',publicKey.export({type:'spki',format:'der'}).subarray(-65).toString('base64url'));console.log('VAPID_PRIVATE=',privateKey.export({format:'jwk'}).d)"
```

**Шаг 2. Прописать переменные в Vercel:**

| Переменная | Что это |
|---|---|
| `VAPID_PUBLIC` | Публичный ключ из шага 1. Не секрет — он и так уезжает в push-службу браузера. |
| `VAPID_PRIVATE` | Приватный ключ из шага 1. **Секрет.** |
| `VAPID_SUBJECT` | `mailto:твоя@почта` — контакт владельца, требование RFC 8292. |
| `SUPABASE_SERVICE_ROLE` | Ключ service_role из панели Supabase. **Секрет.** Только здесь, никогда в клиенте. |
| `PUSH_CRON_SECRET` | Любая длинная случайная строка. **Секрет.** Ей защищена ручка отправки. |

**Шаг 3. Включить расписание в Supabase.** Один раз, в SQL-редакторе.
Подставь свой домен и свой `PUSH_CRON_SECRET` — этот запрос содержит секрет,
поэтому он выполняется вручную и в репозиторий не коммитится:

```sql
create extension if not exists pg_net;

select cron.schedule('push-hourly', '0 * * * *', $$
  select net.http_post(
    url     := 'https://ТВОЙ-ДОМЕН/api/push-send',
    headers := '{"x-push-secret":"ТВОЙ_PUSH_CRON_SECRET"}'::jsonb
  );
$$);
```

Раз в час отправщик спрашивает у базы `push_due()` — кому сейчас пора по
местному времени — и рассылает. Проверить работу расписания:

```sql
select * from cron.job;
select * from cron.job_run_details order by start_time desc limit 10;
```

**Что при этом лежит на сервере:** адрес push-службы браузера, час напоминания,
часовой пояс и дни недели тренировок. Ни веса, ни калорий, ни еды, ни
выполненных тренировок — они зашифрованы и серверу недоступны. Текст
напоминания собирается только из перечисленных полей.

**Web Push собран без зависимостей** — шифрование aes128gcm (RFC 8291) и
подпись VAPID ES256 (RFC 8292) сделаны на встроенном `node:crypto`.
Библиотека `web-push` делает то же самое, но тянуть пакет в проект без
единой рантайм-зависимости незачем.

## 7. Прогон по живому аккаунту (`tests/live.js`)

Задание владельца 21.09: «делай прогон через мой аккаунт, чтоб всё можно было
отслеживать на реальных изменениях». Обычный `tests/browser.js` работает на
выдуманных данных в пустой базе браузера. Живой прогон — то же приложение из
`dist/`, но подключённое к настоящему Supabase: вход, расшифровка хранилища,
рендер реальных дней. Видно ровно то, что владелец видит на телефоне.

### Как передать доступы (и почему не в переписку)

**Пароль в этом приложении — не просто вход.** Из него выводится ключ, которым
расшифровывается всё хранилище (`creds()` → PBKDF2 → обёртка DEK). Пароль,
сказанный агенту в чат, — это не «доступ к аккаунту», а ключ ко всем данным о
здоровье, и он останется в расшифровке разговора, в логах сессии и в claude-mem
(который пишет всё, что агент читает). Поэтому его туда не пишут.

Два способа, оба без участия агента:

```bash
cp .env.example .env.local     # и впиши BV_LIVE_EMAIL и BV_LIVE_PASS
```

`.env.local` закрыт в `.gitignore` шаблоном `.env.*`. Скрипт читает его сам —
агент этот файл не открывает.

Либо (для облачных сессий, где файла нет) — переменные окружения среды
Claude Code: **claude.ai → Code → Environments → Default → Environment
Variables**, имена `BV_LIVE_EMAIL` и `BV_LIVE_PASS`. Тогда значения не лежат
файлом вообще и в переписку не попадают ни при каком раскладе.

### Что прогон может и чего не может

```bash
node tests/build.js && node tests/live.js            # войти и показать, что в аккаунте
node tests/live.js --shots --tab=food,train          # + снимки реальных экранов
node tests/live.js --selftest                        # проверить сам замок, доступы не нужны
```

**По умолчанию — только чтение, и это механизм, а не обещание.** Запрет стоит
в прокси, снаружи страницы: любой `POST/PATCH/PUT/DELETE` на `/sb/rest/v1/*`
отбивается кодом 423 до того, как уйдёт в сеть; код приложения до этого места
не дотягивается. `--selftest` это проверяет восемью пробами — включая обратную
половину: с `--write` запись обязана проходить, иначе «замок» окажется стеной,
и это вскроется в день, когда запись понадобится.

**Регистрация запрещена ВСЕГДА, даже с `--write`.** `sbLogin` по замыслу
приложения заводит новый аккаунт, если почта не нашлась, — для человека это
удобно, для прогона это значит, что опечатка в почте создаёт лишнего
пользователя в живой базе.

**Почему это важнее, чем кажется.** `tests/browser.js` пишет фикстуры и
УДАЛЯЕТ записи за неделю (`del('log', …)`). Направить такой стенд на живой
аккаунт — значит потерять настоящий дневник. Здесь это невозможно физически:
прогон не зовёт `syncNow` (он двусторонний и отправил бы локальную пустоту
в облако), а тянет хранилище напрямую и раскладывает его только локально.

Запись включается двумя вещами сразу: флагом `--write` И переменной
`BV_LIVE_WRITE=1`. Одного флага мало намеренно.

### Снимки

Идут в `BV_LIVE_OUT` или во временный каталог профиля, который стирается в
конце вместе с токеном сессии. **В репозиторий они не кладутся никогда** — это
данные о здоровье живого человека. И отдельно стоит помнить: снимок живого
экрана, показанный агенту, попадает в контекст сессии со всем, что на нём
написано.

### Если пароль всё-таки где-то засветился

Сначала смена пароля в приложении (Настройки → Синхронизация) — она
перезаписывает обёртку ключа, данные при этом не трогаются, — и только потом
чистка логов. Порядок именно такой. См. `SECURITY.md`.
