# Bezvody — целевая архитектура и безопасное развёртывание

Решение принято: строим на **реляционном RLS-бэкенде**. Причина — роадмап (ИИ по истории, общий каталог, аналитика, соц-фичи) требует, чтобы сервер читал данные; E2EE это блокирует. Цена сознательная: уходим от абсолютной приватности личных данных в пользу возможностей.

Ниже — целевая картина и безопасный путь к ней. Ничего не ломаем «большим взрывом»: приложение работает, миграция поэтапная и с сохранением данных.

---

## 1. Слои системы

- **Клиент** — PWA (текущий `index.html`, ванильный). Устанавливается на телефон, работает офлайн через кэш.
- **Supabase** — единый бэкенд: Auth (вход), Postgres с RLS (данные заперты по пользователю), RPC-функции (подбор, корзина, цели), позже Edge Functions (ИИ-слой).
- **Vercel** — раздаёт клиент, авто-деплой из GitHub.

Ключевой принцип RLS: каждая личная таблица заперта политикой `user_id = auth.uid()`. Технически сервер данные видит, но ни один другой пользователь — нет. Это и есть «безопасно» для такого приложения.

---

## 2. Модель данных (целевая)

**Личное (под RLS, `user_id = auth.uid()`):**
- `profiles` — цели КБЖУ, настройки. ✅ готово
- `diary_entries` — дневник питания. ✅ готово
- `body_metrics` — вес, замеры. ✅ готово
- `workouts` / `workout_sets` — тренировки (история подходов, RPE). ⏳ мигрировать из vault
- `sleep`, `steps`, `labs` и пр. — по тому же RLS-паттерну. ⏳ по мере переноса

**Общее (читаемо всеми авторизованными):**
- `products`, `product_packages`, `products_public` — каталог + упаковки. ✅ готово
- `recipes`, `recipe_ingredients`, `recipe_macros` — рецепты. ✅ готово
- `product_quality` — метрика качества. ✅ готово

**Логика на сервере (RPC):** `suggest_recipes`, `suggest_day`, `generate_shopping_list`, `suggest_alternatives`, `log_recipe`, `calculate_targets`, `search_products_fuzzy`. ✅ готово

**E2EE-vault** — остаётся опционально как узкий «сейф» для чувствительных заметок, не как основная модель.

## 3. Безопасность — чеклист хардеринга (делаем перед публичным запуском)

1. **Подтверждение email.** Сейчас авто-конфирм (триггер `auto_confirm_email`) — дыра: фейки засорят общий каталог. Убрать. Клиент уже умеет показывать «подтверди почту», так что это безопасно.
2. **Защита от утёкших паролей** — включить в Auth (тумблер в дашборде).
3. **`pg_trgm`** — вынести из схемы `public` в `extensions`, поправить `search_path` у поиска.
4. **`created_by` в products** — закрыть колонку от чтения клиентом (column-grant), чтобы каталог не раскрывал автора.
5. **Ревью RLS** — все личные таблицы: включён RLS + политики только на своё. Проверять `get_advisors` после каждой миграции.
6. **Секреты** — на клиенте только publishable-ключ (ок, так и есть). `service_role` — никогда в клиент; только в Edge Functions.
7. **Верификация каталога** (`verified`, `official`) — только привилегированным путём (Edge Function с service_role), не из клиента.

---

## 4. Окружения и безопасный деплой

Сейчас один Supabase-проект = прод с твоими данными, миграции летят сразу в него. Для «безопасно развернуть» вводим разделение:

- **Схема-как-код.** Все миграции хранить в репозитории (`supabase/migrations/`), а не только в истории Supabase. Тогда база воспроизводима, изменения проходят ревью, откат возможен.
- **Ветка/стейджинг.** Схему сначала катать на Supabase-ветке (branching) или отдельном стейдж-проекте, проверять, потом в прод. Так прод не ломается непроверенной миграцией.
- **Vercel preview.** Каждая git-ветка → свой preview-деплой для проверки, `main` → прод.
- **Бэкапы.** Убедиться, что включены автоматические бэкапы БД (план Supabase).

---

## 5. Миграция vault → реляционка (аккуратно, без потерь)

Самое деликатное. У тебя (и знакомых) данные лежат в зашифрованном vault. Переход:

1. Клиент при входе расшифровывает vault (как сейчас).
2. Разово переносит записи в реляционные таблицы под своим `user_id` (дневник, вес, тренировки).
3. Ставит флаг «мигрировано», дальше пишет напрямую в таблицы.
4. Vault остаётся как бэкап на время перехода; удаляем после подтверждения.

Личные данные при этом выходят из E2EE — это следствие выбора RLS, делаем осознанно и с сохранением копии. Сейчас пользователей мало — идеальный момент.

---

## 6. Фронтенд «на вырост»

Честно: `index.html` на 300 КБ одним файлом — тоже «однодневный» артефакт. Работает, но растить бесконечно один файл нельзя — станет неподдерживаемым.

Рекомендация: **сейчас не переписывать** (риск/затраты не оправданы), но начать модуляризацию — вынести JS в отдельные файлы, позже ввести лёгкую сборку. Приоритет — слой данных, не косметика. Переписывать фронт только когда упрёмся в поддерживаемость.

---

## 7. Фазовый план

**Фаза A — хардеринг (перед любым публичным шагом).** Пункты раздела 3. Низкий риск, высокая отдача.

**Фаза B — схема-как-код + окружения.** Выгрузить миграции в репозиторий, настроить стейдж/ветку и preview-деплои.

**Фаза C — подключить каталог к клиенту.** Ванильный слой доступа на `sbFetch`: поиск/добавление продукта, подбор, корзина — рядом с vault, не вместо.

**Фаза D — миграция vault → реляционка.** Раздел 5, с бэкапом и флагом.

**Фаза E — ИИ-слой и соц-фичи.** Edge Functions поверх готовых данных; качество каталога уже заложено.

Порядок можно двигать, но A всегда первая.
